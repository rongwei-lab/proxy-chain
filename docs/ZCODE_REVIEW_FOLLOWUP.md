## 2. Z01：特殊缺失节点引用仍会白屏

### 2.1 复现步骤

1. 启动前端并加载示例节点，确认已有有效配置输出。
2. 将下面内容保存为 JSON，通过“导入方案 JSON”导入。

```json
{
  "schemaVersion": 1,
  "includesCredentials": false,
  "activePlanId": "review-plan",
  "plans": [
    {
      "schemaVersion": 1,
      "id": "review-plan",
      "name": "复测方案",
      "mode": "simple",
      "entry": {
        "id": "review-entry",
        "name": "入口",
        "enabled": true,
        "candidateNodeIds": ["constructor"],
        "strategy": "select"
      },
      "relays": [],
      "exit": {
        "id": "review-exit",
        "name": "出口",
        "enabled": false,
        "candidateNodeIds": [],
        "strategy": "select"
      },
      "routingPreset": "cn-direct",
      "customRules": [],
      "customFallbackTarget": {
        "kind": "plan",
        "planId": "review-plan"
      }
    }
  ],
  "sources": []
}
```

**实际结果：** 文件通过结构校验，随后页面白屏。浏览器异常为：

```text
Cannot read properties of undefined (reading 'type')
```

调用位置：`src/lib/orchestrator.ts` 的 `buildChainPreview`，当前在 `registry[nodeId]` 后读取 `entry.node.type`。

### 2.2 根因

`registry` 使用普通对象。当不存在名为 `constructor` 的自有节点时，`registry['constructor']` 仍读到对象继承属性；`if (entry)` 把它当成有效节点，随后访问不存在的 `entry.node`。

这不是仅修正 JSON 数组元素类型就能解决的问题。预览、校验、导出和节点提示的字典访问都应正确区分自有数据与继承属性。

### 2.3 修复要求

- 节点字典可使用 Map、无原型字典或统一的自有属性读取函数；不得仅依赖 `if (registry[id])` 判断节点是否存在。
- 检查其他相关读取入口，包括节点预览、拓扑校验、节点链接导出、来源合并、恢复，以及 `nodeHints` 等按外部标识索引的对象。
- 对于外部标识参与对象构造/赋值的地方，也要确保特殊键不会改变字典原型或被误当成已有数据。
- 文件校验可以拒绝不符合项目标识约定的输入，但不能把只过滤 `constructor` 这一个字符串作为全部保护。
- 合法但不存在的节点引用继续按“待重新绑定/已失效”处理，阻止完整链路导出，不自动改成直连，不使页面崩溃。
- 若导入文件被判为无效，保留当前工作区并显示可读错误；若允许恢复为待补全状态，页面必须可继续编辑。两种处理都不能出现白屏。
- 当前正常的无凭据方案、失效引用提示，以及同名节点处理保持可用；不要为规避问题拒绝所有缺失引用。

### 2.4 必需回归测试

| 用例 | 输入/操作 | 预期 |
| --- | --- | --- |
| Z01-T01 | 导入上述 `constructor` 文件 | 显示拒绝原因或待补全状态，页面不白屏 |
| Z01-T02 | 节点引用分别为 `toString`、`__proto__`、`hasOwnProperty` | 不将继承属性当成节点，不异常导出 |
| Z01-T03 | 预览、校验、方案链接与节点库链接读取同类缺失引用 | 各入口采用相同的安全读取规则，无未捕获异常 |
| Z01-T04 | 节点提示或附带节点数据中含特殊标识 | 按明确校验规则拒绝或安全处理，不改变字典原型、不伪造有效节点 |
| Z01-T05 | 普通缺失引用、正常无凭据方案和有效方案 | 缺失时可编辑并阻止不完整导出；正常输入保持可用 |

## 3. Z02：撤销不能恢复其他来源已移除的关联

### 3.1 复现数据

使用两个来源 A、C，以及两个不同连接 N、M：

```text
N = socks5://demo:REDACTED@old.example.invalid:1080#original
M = socks5://demo:REDACTED@new.example.invalid:1080#newer
```

操作顺序与期望状态：

| 步骤 | 来源 A 的节点 | 来源 C 的节点 | 节点 N 应关联的来源 |
| --- | --- | --- | --- |
| A、C 均导入 N | N | N | A、C |
| 删除 A | 来源不存在 | N | C |
| 刷新 C，结果只包含 M | 来源不存在 | M | N 不在节点库中 |
| 撤销 A 的删除 | N | M | 仅 A |
| 再次删除 A | 来源不存在 | M | N 不在节点库中 |

**实际结果：** 撤销后 N 的 `sourceIds` 变为 A、C，虽然 `C.nodeIds` 已不包含 N；再次删除 A 后，N 仍因错误的 C 关联被保留。

复测在核心模块中依次调用了 `upsertSourceNodes`、`removeSourceFromWorkspace`、`restoreDeletedSource`，没有依赖真实订阅请求。

### 3.2 根因

`src/lib/orchestrator.ts` 的 `restoreDeletedSource` 按“来源 ID 当前仍存在”筛选旧快照中的来源关系，然后把这些旧关系一起恢复。来源 C 仍存在，不代表它现在仍提供节点 N。

### 3.3 修复要求

- 撤销只为本次恢复的来源 A 添加它的节点关联和来源别名，不从旧快照恢复其他来源关系。
- 当前节点已存在：以当前条目为基础，仅补入 A；保留最新节点数据、用户别名、其他来源关系及其别名。
- 当前节点不存在：恢复 A 提供的节点，初始来源关系仅包含 A。不能因为旧快照中还有 C，就自动加回 C。
- 其他来源对 N 的保留、移除、替换与凭据变更，以其当前成功解析结果为准。
- 保持双向关联一致：恢复操作不能使 `registry[N].sourceIds` 声称由 C 提供，而 `C.nodeIds` 中没有 N。
- 来源别名映射不得保留被错误恢复的其他来源项。节点选择及方案引用不因撤销而回滚到旧状态。
- 保留上一轮修复：撤销不覆盖期间新增来源 B、其他来源刷新结果、用户编辑和会话订阅 URL；重复撤销不产生重复数据。

### 3.4 必需回归测试

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| Z02-T01 | 完整执行上表流程 | 撤销后 N 仅关联 A；再次删除 A 后 N 消失 |
| Z02-T02 | 删除 A 后 C 仍保留 N，但刷新了其他数据或修改了别名 | 恢复 A 不回滚 C 的最新数据与用户编辑 |
| Z02-T03 | 删除 A 后再删除 C，然后恢复 A | 不复活 C，也不恢复 C 的别名关联 |
| Z02-T04 | N 还由 D 提供；删除 A 后 C 移除 N，再恢复 A | N 仅关联当前的 D 和恢复的 A，不包含 C |
| Z02-T05 | 删除 A 后新增 B、修改方案，再撤销 A 或重复撤销 | B、方案和现有会话数据保留，不重复追加节点 |

在恢复后、再次删除后分别断言节点库与来源列表的关联，不仅检查来源名称重新出现。

## 4. Z03：旧版方案文件的自定义别名迁移

### 4.1 复现条件与步骤

旧版 `schemaVersion: 1` 的节点条目包含 `displayName`、`sourceAliases`，但没有本次新加的 `userAlias`。例如来源原名是 `original`，用户显示别名是“历史自定义别名”。

可在测试中按以下步骤构造旧文件：

1. 导入上文的节点 N，创建一个引用 N 的有效方案。
2. 用现有重命名函数把 N 的显示别名改成“历史自定义别名”。
3. 用 `serializeWorkspaceState` 生成含凭据的正常方案包。
4. 从包内的节点条目中删除新增的 `userAlias` 字段，保留 `displayName`、`sourceAliases` 和其他内容，以模拟旧格式。
5. 用 `validateAndRestoreWorkspace` 恢复，确认界面/模型仍显示“历史自定义别名”。
6. 用原来源 ID 和相同连接内容调用 `upsertSourceNodes` 模拟刷新。

**实际结果：** 文件可以恢复，但刷新后显示别名变回 `original`。

这项问题通过核心 API 复现。当前恢复文件不会保存订阅 URL；如果做页面复现，需要重新导入/绑定来源，不要把“暂时无法刷新旧订阅”当成别名迁移已正确。

可选页面路径：恢复旧文件 → 为同一连接新增订阅来源 → 删除恢复文件里的旧来源 → 刷新新增来源，检查历史别名是否仍保留。

### 4.2 根因

`restoreManagedNodeEntry` 只按原样读取可选的 `userAlias`。旧文件没有该字段时，虽然 `displayName` 被保留，但没有迁移为有效的用户覆盖。后续单来源刷新仅根据 `userAlias` 保留别名，因此重置显示名。

### 4.3 修复要求

- 对正常旧版 schemaVersion 1 节点条目补充明确的兼容迁移，不能只保证新版生成文件的保存/恢复。
- 存在有效 `userAlias` 时，以显式用户覆盖为准，并保持恢复后的显示状态一致。
- 缺少 `userAlias` 时，结合 `displayName`、历史来源别名等信息判断是否有用户覆盖。例如显示名不同于所有来源原名时，应保留为用户覆盖。
- 历史信息不足以可靠区分时，优先保留已有非空显示名并明确兼容策略，不悄悄恢复成订阅原名。
- 不要不加区分地把所有无 `userAlias` 的新版默认名称都永久固化为用户覆盖；没有用户覆盖的正常来源改名仍按现有规则处理。
- 迁移不改变连接身份、凭据、稳定节点 ID 或方案选择。不按同名自动继承另一条连接的身份。
- 迁移后的别名在刷新、共享来源合并/删除、撤销和再次保存/恢复后保持一致。
- 保持 schemaVersion 1 正常文件兼容；不要求为解决本问题重写文件格式或更换持久化工具。
- 默认不保存凭据的策略保持不变。未附带节点正文的结构文件仍显示待补全，不自动创建无凭据的可连接节点。

### 4.4 必需回归测试

| 用例 | 数据/操作 | 预期 |
| --- | --- | --- |
| Z03-T01 | 旧文件有自定义 displayName、无 userAlias → 恢复 → 相同来源刷新 | 历史别名、节点 ID 和方案选择保持 |
| Z03-T02 | 旧文件恢复后，来源原名变化但连接不变 | 历史用户别名仍优先，来源原名信息更新 |
| Z03-T03 | 正常默认名称与显式新版 userAlias 分别恢复 | 无覆盖时遵循来源命名规则；有覆盖时保留用户别名 |
| Z03-T04 | 旧文件迁移 → 新增/删除共享来源 → 刷新/撤销 → 再保存恢复 | 别名不丢失，来源关系正确，无旧快照覆盖 |
| Z03-T05 | 旧版无凭据结构文件，以及同名但连接凭据变化 | 结构文件保持待补全；不同连接不静默继承身份或移接选择 |
