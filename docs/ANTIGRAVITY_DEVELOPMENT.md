## 1. 开发目标与执行方式

将当前固定的“入口 + 出口”配置生成流程，扩展为支持以下场景的工具：

1. 只使用入口节点，独立出口可关闭。
2. 追加多个订阅、粘贴内容或手动节点，统一管理和筛选。
3. 多个入口作为候选，在客户端中选择一个使用。
4. 配置入口选择策略、保存多套方案、选择分流模板，并提供不同导出方式。
5. 在高级模式中增加中转层，按顺序形成多级链路。

默认按照 M0 → M1 → M2 → M3 顺序开发，允许按里程碑交付。M0 + M1 是首个可独立验收版本；M2、M3 也属于本文规划范围，未实现时必须明确标记，不得将部分完成称为全部完成。

## 3. 默认产品决策

1. **出口可选**指“独立出口可关闭”。关闭后，最后一个启用的入口或中转层承担最终出口角色，代理流量仍通过该链路访问目标。
2. **追加入口候选**与**增加串联中转层**是两个独立功能。候选列表中每次选择一个节点；中转层按顺序全部经过。
3. 兼容已有使用方式：已有“入口 → 出口”场景保持可用，初始仍显示该模式，独立出口默认开启。
4. 禁用的层保留编辑内容和选择状态，但不进入本次导出，不影响当前有效链路的校验。
5. 首批配置验收以 Mihomo 为目标。其他客户端必须单独标注能力与验证状态，不将支持 Mihomo 等同于支持所有名为 Clash 的客户端。
6. v2rayN 暂保持操作指南；完整接入 Xray JSON 属于另行开发的客户端适配项，不在本轮增加新的自动导出承诺。
7. Shadowrocket 等客户端的链式导入能力未完成实测，现有说明需准确标注，不宣称已通过兼容性验收。
8. 默认只在当前会话处理输入，不自动持久化凭据，不后台轮询订阅。用户主动保存或生成临时链接时，按具体行为说明数据去向。

## 4. M0：Bug 修复

### B01：YAML 序列化改变字符串值

**证据：已复现。** `src/lib/proxy-chain.ts` 中的 `formatYamlScalar` 仅对部分特殊字符加引号，密码 `"001234"` 导出后重新解析为数字 `1234`。布尔值、空值和科学计数法形式的字符串也需要覆盖。

**修复要求：**

- 使用已有 `yaml` 依赖序列化结构化对象，替代不完整的手写 YAML 标量规则。
- 密码、用户名、UUID、Reality short-id、插件参数等字符串必须保留类型和内容，不能通过数值转换丢失前导零。
- 不改动真实数字、布尔字段的类型。
- 若输入的 UUID、密码等字段已被 YAML 解析成非字符串且无法可靠还原原文，给出字段错误，不能猜测原值。

**验收：** 对 `"001234"`、`"true"`、`"false"`、`"null"`、`"1e3"`、含空格、换行、引号和 `#` 的字符串，执行“解析 → 导出 → YAML 重新解析”，类型、值均保持一致。测试断言结构和值，不依赖特定引号样式。

### B02：协议关键参数丢失或被错误补全

**证据：已复现并结合代码确认。** VLESS 归一化未保存 Reality `sid`；YAML 中的 `reality-opts.short-id` 也未保留。WebSocket 的 `path`、`host` 未保留。Clash 导出固定写 `tls: true`，库中的 Xray 导出固定使用 Reality 安全层。

**修复要求：**

- 扩展现有归一化类型，区分 VLESS 的 `none`、`tls`、`reality`，保留必要的 TLS、Reality 和传输参数。
- URI 的 `sid` 与 Mihomo 的 `reality-opts.short-id` 正确映射，保持字符串及前导零。
- 保留已支持传输的完整连接参数，包括 WebSocket 的路径、Host，以及声明支持的 gRPC 参数；未实现的传输必须明确提示，不静默降级到 TCP。
- 支持的安全层和传输类型必须形成能力表。对于未知但可能影响连接的字段，保留可识别的数据并提示；无法正确转换时阻止对应格式导出。
- SS 插件及选项、Hysteria2 的 SNI 与证书校验参数等，也必须按目标格式校验并保留；不能仅识别协议名称就视为完整支持。
- 修复库中现有 Xray 生成函数的同类数据问题，不因此自动将其接入页面或声称支持全部协议组合。

**验收：** 同时覆盖 URI 和 YAML 输入；Reality short-id、TLS、无 TLS、WebSocket 路径与 Host 均符合预期；Clash YAML 和普通节点链接分别验证。未支持组合必须出现明确提示，不能生成看似成功但缺少关键字段的配置。

### B03：订阅重定向绕过目标校验

**证据：代码确认，未做线上利用验证。** Node 与内部 Worker 都仅校验初始 URL，之后使用 `redirect: 'follow'`，后续目标不再执行域名白名单和地址校验。

**修复要求：**

- 禁止不受控自动跟随重定向。使用手动跳转，解析相对 `Location` 后，对每一跳重新执行协议、主机白名单及适用的地址检查。
- 默认最多跟随 5 次跳转；缺失或无效 `Location`、跳转循环、超限时明确失败。该数值是本项目默认值，可通过配置调整。
- 保持默认 12 秒总超时和 2 MiB 响应上限；总超时覆盖整个跳转与读取过程，不能每跳重新开始计时。
- Node 使用可靠的 IP/CIDR 判断，覆盖完整 loopback 范围、私网、链路本地、IPv6 及 IPv4 映射地址，不能只比较 `127.0.0.1`。
- Node 的 DNS 检查需与实际连接地址绑定，避免“预检一次、连接时重新解析”的竞态。固定连接地址时保留正确的 Host、TLS SNI 和证书校验。不要仅增加一次 DNS 查询就宣称已解决 DNS 重绑定，也不要通过关闭 TLS 校验绕过连接问题。
- Worker 根据运行时能力执行每跳白名单与地址字面量检查；无法执行的 DNS/网络层检查要记录限制，不能虚构与 Node 完全相同的防护能力。
- 不向上游订阅服务器转发服务访问 token；错误、日志和测试报告不得泄露完整订阅 URL 或凭据。
- 超时、超限或失败时取消上游读取并释放资源。继续沿用现有来源和认证边界，不放宽允许域名。

**验收：** 使用受控的本地服务、请求模拟和 DNS 模拟覆盖：允许域名跳转到允许域名、非白名单域名、内网地址、相对跳转、循环、超时、超限、IPv6。测试不得访问真实内网资源。

参考：[OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

### B04：临时 Clash 导入链接依赖单机房缓存

**证据：架构风险，未在线复现。** `cloudflare/app-worker.js` 将配置仅写入 `caches.default`，读取未命中就返回 404。Cloudflare 官方明确 Cache API 内容不跨来源数据中心复制，因此不能据此承诺任意客户端都能读取已创建链接。[官方说明](https://developers.cloudflare.com/workers/runtime-apis/cache/#background)

**修复要求：**

- 将临时配置访问封装成独立存储接口；权威数据不得仅保存在边缘 Cache。
- 默认技术方案为 Durable Object：根据随机配置 ID 路由到同一对象，保存配置正文、`createdAt` 和 `expiresAt`。不同边缘入口需访问同一个权威记录。
- 默认访问有效期仍为 600 秒，读取时检查绝对过期时间，不因读取而续期；到期后接口不再提供配置，并安排后台清理。
- 保留至少 192 bit 的随机 ID，不包含密码、订阅 URL 或可枚举的递增编号。链接持有者在有效期内可读取配置，这一点必须明确说明。
- 私密配置响应使用 `Cache-Control: no-store`，避免额外的公共缓存副本；GET 与 HEAD 的状态、内容类型、过期行为一致。
- POST 在读取请求体时执行 2 MiB 上限，不能只依赖 `Content-Length`；格式错误返回 400，超限返回 413，存储异常返回 503，缺失或过期返回 404。
- 更新 Worker bindings、迁移配置、本地开发配置及 README；明确新方案会把配置写入服务端存储，不能继续宣称“不写入服务端存储”。
- **600 秒指访问有效期，不等于平台备份中的物理删除期限。** 若使用 SQLite-backed Durable Object，需结合平台恢复/备份机制如实说明保留行为，不宣称到期后所有副本立即消失。[存储与恢复语义](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- 未配置所需存储时，健康接口应声明临时链接能力不可用；前端禁用该操作，仍允许本地复制和下载。

**验收：** 用两个独立前端/边缘处理实例访问同一权威存储，验证“创建后立即读取”、HEAD、过期、存储故障和并发读取。该集成测试不能写成两个实例共享同一个 JavaScript 缓存 Map 后就宣称跨机房已验证。真实跨地区访问另列线上验收，未执行时明确标记。

### B05：健康检查把 HTML 200 当作服务可用（补充修复）

**修复要求：** 校验 JSON 内容类型、应用身份、成功字段和能力字段；设置请求超时和卸载取消；分别判断订阅拉取与临时配置能力。健康检查只表明接口和绑定能力，不代表任意订阅域名或节点一定可用。


**验收：** HTML 200、无关 JSON、无效 JSON、超时、缺失绑定均不能使相应功能显示可用；静态站点不显示可用的后端导入按钮。未知 `/api/*` 路径返回 API 错误，不返回 SPA HTML 作为成功响应。

### B06：不同凭据节点被误去重（补充修复）

**证据：已复现。** `dedupeNodes` 仅使用协议、服务器、端口和名称。相同名称和地址、密码不同的两个 SOCKS5 节点，解析后只剩一个。

**修复要求：** 去重依据包含完整连接语义：认证、加密、TLS、Reality、传输、插件等。相同显示名不能决定连接身份；同一服务器不同凭据必须保留。相同连接从多个来源导入时可以合并，但保留所有来源关联；节点 ID 不直接包含凭据，重命名不改变连接身份或丢失选择。

**验收：** 覆盖不同密码、UUID、SS cipher、Reality short-id 和传输参数；确实相同的连接合并来源；移除一个来源不误删仍被其他来源提供的节点。

## 5. M1：首批功能

### F01：独立出口开关

- 在链路设置中增加“使用独立出口”开关，默认开启以兼容现有流程。
- 关闭后折叠出口设置并保留内容；导出不包含该出口节点、分组或对它的引用。
- 没有启用中转时，关闭独立出口意味着入口承担最终出口；不能因此把代理流量改为 `DIRECT`。
- M3 增加中转后，关闭独立出口意味着最后一个启用的中转层承担最终出口。
- 切换开关立即更新路径、校验结果、预览和按钮可用状态。

| 入口有效选择 | 独立出口 | 出口有效选择 | 配置导出行为 |
| --- | --- | --- | --- |
| 至少 1 个 | 关闭 | 任意，包括为空或旧内容无效 | 允许生成，最终匹配入口组；启用中转后匹配最后一个中转组 |
| 至少 1 个 | 开启 | 至少 1 个 | 允许生成“入口 → 出口”链路 |
| 至少 1 个 | 开启 | 0 个 | 阻止导出，提示选择出口 |
| 0 个 | 任意 | 任意 | 阻止导出，提示选择入口；不自动将出口改成入口 |

验收需包含“开启 → 关闭 → 再开启”，证明出口输入和选择仍在，但关闭期间不存在于导出配置中。高级模式下任一启用中转层为空时也必须阻止导出。

### F02：多个节点来源追加与管理

支持三类来源：“添加订阅”“粘贴节点/配置”“手动添加节点”。手动表单按协议展示必要字段，节点来源与入口/出口角色分开管理；用户从来源中选择节点加入链路。

具体行为：

1. 每个来源有独立名称、类型、解析数量、状态和删除入口；订阅来源另有刷新按钮及最后成功刷新时间。
2. 新增来源采用追加方式，不替换已有来源。多个来源的有效节点进入统一候选列表。
3. 订阅刷新仅在用户主动点击时发生；失败保留上一次成功结果，不清空已有节点。
4. 刷新采用完整结果校验后再替换该来源。不能将网络失败、HTML 错误页或无法识别的内容当作成功覆盖。
5. 首次创建方案时可沿用“默认选择第一个有效节点”；之后追加或刷新不重置已有选择，不悄悄改选其他节点。
6. 刷新后所选连接确实消失或凭据改变时，标记该引用失效并提示重新选择；不能仅按同名节点自动替换连接。
7. 删除来源前展示它影响的节点和方案引用，提供取消或撤销；若节点仍由其他来源提供，不能误删。
8. 每个来源独立管理请求取消及请求版本，旧请求不能覆盖较新的刷新、编辑或删除结果。
9. 解析结果显示“有效／不支持／无效”的数量及原因。支持部分有效内容时可以保留有效节点，但不得隐瞒其余节点被忽略。
10. 当前服务拉取的域名白名单限制继续保留；不为兼容任意新来源而放开后端限制。

首批继续支持现有 URI 列表及 YAML 输入。不将整段 Base64 订阅、新协议或其他客户端配置格式默认视为已经支持；如扩展，补充能力表、样例和测试。

### F03：节点搜索、筛选与批量选择

- 按名称、协议、来源筛选；名称搜索大小写不敏感。
- 列表展示名称、协议、服务器/端口和来源；默认不展示密码、UUID 或订阅 token。
- 明确区分“候选总数”“筛选结果数”“已选数量”。
- 筛选不改变已有选择；清除筛选后，之前选中的节点仍选中。
- “全选”明确为“全选当前结果”，只影响当前筛选结果；“清空当前结果选择”也只作用于当前结果，另提供显式清空整层选择。
- 同名不同连接可分别选中，并用地址、协议或来源帮助区分。
- 入口、出口和中转层都复用该选择能力，不分别复制一套业务逻辑。

### F04：实时链路预览

示例：

```text
本机 → 入口候选组（3 选 1）→ 目标网站
本机 → 入口候选组（3 选 1）→ 独立出口（住宅节点）→ 目标网站
本机 → 入口 → 中转 1 → 独立出口 → 目标网站
```

- 候选节点画在同一层；不能将同一层候选 A、B 误画成 A → B。
- 明确标出最终出口来自哪一层，并显示当前配置的选择策略。
- 停用的层不进入有效路径，可在编辑区显示“已停用，内容已保留”。
- 预览代表配置路径；没有读取客户端运行状态时，不声称知道客户端实际选中了哪一个节点。
- 缺少必填层时显示待补全位置；同步更新配置预览，不保留误导性的旧成功状态。

### F05：导出前校验与诊断

在复制完整配置、下载完整配置和创建临时链接之前使用同一套校验逻辑。导出结果与校验对象必须来自同一份方案快照。

阻断校验只针对本次导出所引用的有效层及依赖；停用层或未被引用来源的问题可以在编辑区提示，但不能阻止一套本身有效的方案导出。

至少检查：

- 有效入口、启用出口及启用中转层是否为空。
- 节点必填字段、端口范围、字段类型、目标格式是否支持当前参数。
- 节点或来源删除后是否存在失效引用。
- 全局导出名称、分组引用是否唯一且完整。
- 链路是否自引用、循环或在不同层重复使用同一连接；多个不同方案复用节点本身不构成循环。
- 协议组合及传输能力是否匹配；UDP/QUIC 相关能力按目标客户端验证，不能仅凭一个 `udp: true` 就判为兼容。
- 未支持、已忽略但可能影响连接的字段。

诊断分为错误与警告，定位到方案、来源、层或字段。错误阻止对应导出；警告说明影响，不伪造连接检测结果。对无法确认兼容性的关键连接参数，按错误处理，不静默生成。

普通节点链接可以独立导出已选择且有效的节点，不要求它们已组成完整链路；必须明确该结果不包含串联关系。

## 6. M2：增强功能

### F06：入口选择策略

入口层提供以下选择，默认手动选择：

| 策略 | 目标语义 |
| --- | --- |
| 手动选择 `select` | 用户在客户端中选择入口候选 |
| 自动选择 `url-test` | 客户端按探测结果自动选择，允许设置探测 URL、间隔和切换容差 |
| 故障切换 `fallback` | 客户端按候选顺序选择可用入口，允许设置探测 URL 和间隔 |

探测和自动切换由导出的配置交给客户端执行，网页不显示虚构的节点延迟或“已测速”。出口默认维持手动选择，避免默认自动改变出口 IP；若开放出口策略，必须让用户明确选择并提示影响。

参数做范围与格式校验；链路生成与策略选择解耦，单入口仍能正常生成。具体语义参照 Mihomo 的[手动选择](https://wiki.metacubex.one/config/proxy-groups/select/)、[自动选择](https://wiki.metacubex.one/config/proxy-groups/url-test/)与[故障切换](https://wiki.metacubex.one/config/proxy-groups/fallback/)文档。

### F07：多套命名方案与主动保存

- 支持新建、重命名、复制、切换、删除方案，例如“日常使用”“住宅出口”。
- 方案复用节点来源，各自保存入口、出口开关、候选选择、策略、分流设置；修改一个方案不意外影响其他方案的编排。
- 默认只保留在内存。用户主动选择保存到本机后才持久化，并能一键清除。
- “保存方案结构”默认不含节点密码、UUID、完整订阅 URL、原始配置和服务 token；缺少所需节点时恢复为“需要重新导入/绑定”，不能改成直连。
- 如用户主动选择保存完整凭据，提前明确保存内容和明文/加密方式；本地存储不能直接标为“已加密”。外部服务访问 token 继续仅保留在会话中。
- 导入/导出方案文件提供 `schemaVersion`，校验结构、大小和引用；默认文件不含凭据，含凭据版本由用户显式选择并清晰标注。
- 显示名相同、导入顺序改变、来源重复时，方案引用仍可明确识别或提示重新绑定。

### F08：分流模板

提供以下模板，默认保留现有“国内直连”行为：

1. **全代理规则**：业务流量的最终规则指向方案的最终有效层。
2. **国内直连**：保留国内直连规则，其他流量走最终有效层。
3. **自定义域名分流**：支持域名/域名后缀指向指定方案、直连或拒绝，并调整规则顺序。

要求：

- 校验规则目标及优先级；引用不存在或没有有效链路的方案时阻止导出。
- 多方案合并导出时生成互不冲突的节点/分组名称，并加入必要依赖。
- 明确区分流量分流与 DNS 配置，不将 `MATCH` 规则等同于“所有 DNS 请求也经代理”。DNS 配置随完整配置明确展示，不在后台随模板悄悄切换。
- 不引入远程规则源自动下载或在线规则编辑服务作为必需依赖。

### F09：多种导出方式

| 方式 | 输出与限制 |
| --- | --- |
| 完整 Mihomo 配置 | 包含选中方案所需的节点、组、规则和本地运行设置；保留当前复制、下载能力 |
| 合并用配置片段 | 只给出节点、组和需要接入的规则，不带会覆盖用户现有端口/DNS 的完整运行设置；附简短接入说明 |
| 普通节点链接 | 只包含节点连接信息，明确不包含选择组、分流和串联关系 |
| 按方案批量下载 | 每套方案独立生成且先校验；文件命名可区分，不混用相同名称或内容 |
| 一键导入 Clash | 使用 B04 的临时链接能力；后端不可用时提供复制、下载，不显示导入成功 |

不要把 YAML 文本直接拼接当作配置合并。此功能要求输出可供合并的片段，不要求额外实现一个自动修改用户现有配置的编辑器。

所有导出使用统一的编排、名称分配和诊断结果。普通链接或配置可能含凭据，文件名、URL 参数和日志不能附加原始密码。v2rayN 使用指南与未经实测的其他客户端能力单独呈现。

从方案导出普通节点链接时，默认只包含启用层选择的节点；从节点列表单独导出时，可以不要求存在完整方案。两种入口都不应悄悄包含已停用的层。

## 7. M3：高级链路编排

### F10：增加、排序与停用中转层

- 增加“简单模式／高级模式”。简单模式仍为入口与可选独立出口，不暴露多余设置。
- 高级模式允许在入口之后、独立出口之前添加中转层；每层有独立名称、候选节点、选择策略和启用状态。
- 支持添加、删除、拖动排序；同时提供上移、下移按钮，兼顾键盘和移动端操作。
- 入口必需且始终启用；独立出口继续使用 F01 开关；中转层可以单独停用并保留内容。
- 第一版产品上限设为 5 个启用层，包含入口和启用的独立出口；这是本项目的交互限制，不是协议限制。
- 从高级模式切回简单模式时保留中转编辑数据，明确本次导出暂不使用这些层；再返回高级模式可恢复。

生成语义：

1. 先按界面顺序得到实际启用的层：入口 → 中转 1 → … → 可选独立出口。
2. 入口不添加新的上游代理依赖；后续每一层中的节点通过 `dialer-proxy` 引用前一层的选择组。
3. 代理业务流量最终匹配最后一个启用层；没有独立出口时不引用空出口组。
4. 同一个基础节点用于不同方案或不同编排时，按方案/层生成独立导出实例，不能通过修改共享节点对象污染其他链路。
5. 第一版直接阻止同一连接同时出现在同一路径的不同层中，防止某种候选组合形成自引用。多个方案之间的正常复用允许。
6. 任何尚未验证的关键协议组合需提示并阻止对应自动导出；不保证所有支持的协议任意排列都能连通。

Mihomo 允许 `dialer-proxy` 引用节点或策略组，可作为编排实现基础，但实际多层组合仍需单独验证。[官方配置语义](https://wiki.metacubex.one/config/proxies/dialer-proxy/)

## 8. 数据结构与实现约束

### 8.1 状态模型

将“节点来源”“归一化节点”“方案编排”“导出配置”分开。下面是建议结构，不是当前仓库已有类型；字段命名可沿用项目约定，但必须保留这些概念和边界：

```ts
type SourceKind = 'subscription' | 'paste' | 'manual'
type SelectionStrategy = 'select' | 'url-test' | 'fallback'
type RoutingPreset = 'all-proxy' | 'cn-direct' | 'custom'

interface NodeSource {
  id: string
  name: string
  kind: SourceKind
  nodeIds: string[]
  status: 'idle' | 'loading' | 'success' | 'failed'
  lastSuccessAt?: string
  // URL、原始内容等敏感字段单独管理，不默认进入持久化数据。
}

interface ChainStage {
  id: string
  name: string
  enabled: boolean
  candidateNodeIds: string[]
  strategy: SelectionStrategy
  probe?: { url: string; intervalSeconds: number; toleranceMs?: number }
}

interface ChainPlan {
  schemaVersion: 1
  id: string
  name: string
  mode: 'simple' | 'advanced'
  entry: ChainStage
  relays: ChainStage[]
  exit: ChainStage // enabled 即“使用独立出口”开关。
  routingPreset: RoutingPreset
  // 自定义规则使用有类型、可校验的单独结构。
}
```

继续使用并扩展现有协议判别联合类型，不以无约束 `any` 代替归一化模型。来源与节点为多对多关系，需要保留来源关联及显示别名。节点连接身份、显示名、导出名分别处理，不能互相替代。

### 8.2 核心数据流

```text
来源输入/主动拉取
  → 解析、字段校验、归一化
  → 节点注册表与来源关联
  → 方案引用节点，得到启用层
  → 目标能力校验、名称分配、编排
  → 结构化配置对象
  → yaml/JSON/URI 序列化
  → 预览、复制、下载或用户主动生成临时链接
```

- 解析、编排、校验和生成保持可独立测试的纯逻辑；网络请求、本地保存和客户端唤起放在边界层。
- 旧的双节点生成接口可保留为包装，避免不必要地破坏现有调用；新增场景使用方案模型，不能仅把 `exitNode` 改成可空后在各处散落条件分支。
- 显式的 VLESS `security` 优先；旧输入只含 `pbk`、未写 `security` 时，可为兼容已有测试推断 Reality。缺少其他关键参数时仍需诊断，不一律开启 TLS。
- 分配导出名称时避开所有节点、组和保留名称的冲突，包含不同方案/层的复用场景。
- 普通输入不可直接注入任意 `dialer-proxy` 或分组引用；链式依赖由当前方案生成。
- 不因改变界面语言、筛选条件或显示名而丢失选择；不在每次 React 渲染时重新分配已有节点 ID。
- 不要求引入新的全局状态库；仅在现有方式无法清楚维护时选用轻量依赖，并说明理由。

### 8.3 界面建议

桌面端按以下内容组织，可根据现有布局采用两列或三列，不要求重做整套视觉设计：

| 区域 | 主要内容 |
| --- | --- |
| 节点来源 | 添加来源、刷新/删除、搜索筛选、节点列表 |
| 链路设置 | 方案切换、入口选择、出口开关、中转层、策略、路径预览 |
| 预览与导出 | 目标格式、诊断、配置、复制、下载、临时导入 |

移动端按相同阅读顺序纵向排列。表单有可访问名称，开关、筛选和排序支持键盘；中英文文案同步。空状态、加载状态、部分解析成功、失败保留旧数据等状态都应有明确反馈。

### 9.2 测试方式

- 复用现有 Vitest；把以 `toContain` 为主的导出测试补充为 YAML/JSON 结构和引用关系校验。
- 为页面交互增加必要测试，重点覆盖状态组合和异步竞态，不编写只重复实现步骤的脆弱测试。
- Node 和 Worker 的请求、重定向、大小限制、错误映射分别测试；只测前端库不足以覆盖后端修复。
- Worker 需要运行时集成测试覆盖 Service Binding、存储绑定及缺失绑定。选择官方支持方式时，先核对其与当前 Vitest/Vite/Wrangler 版本的兼容性。
- 服务端 `.js`、`.mjs` 目前未被现有 TypeScript 文件匹配的 lint 规则完整覆盖；修改时应补充适用规则或独立语法/集成检查，不能把现有 `npm run lint` 通过当作 Worker 已被检查。
- 使用脱敏输入：`example.invalid`、文档保留地址、全零 UUID、`REDACTED_*`；不要将真实订阅、节点或 token 放入 fixture、快照或报告。
- 真实客户端验证由受控测试节点或所有者授权的节点完成；单纯配置语法通过不等于链路可连通。
- 页面测试不得为了“验证成功”自动唤起真实 VPN、改系统代理或修改所有者已有客户端配置。

### 9.3 开发完成后的关键命令

现有项目命令如下，开发后重新执行并记录结果：

```bash
npm ci
npm run typecheck
npm run lint
npm run test
npm run build
```

新增 Worker/Node 测试如需单独脚本，补入 `package.json` 并在报告中给出实际命令。使用本地 Worker 集成测试、构建检查或 Wrangler 支持的本地 dry run 验证配置；生产部署不是测试通过的前提，也不能未经授权执行。
