## 3. R01：撤销删除只恢复目标来源

### 3.1 复现与影响

1. 点击“加载示例节点”，得到“示例入口池”和“示例落地池”。
2. 删除“示例落地池”，确认删除，但暂不撤销。
3. 新增一个粘贴来源，命名为“删除后新增的来源”，输入：

```text
socks5://demo:REDACTED@new.example.invalid:1080#新增节点
```

4. 点击“解析并添加到节点库”，确认新来源存在。
5. 点击“撤销删除”。

**实际结果：** 示例落地池恢复，但刚新增的来源及节点消失。期间对其他节点进行的重命名、刷新等操作也可能被回滚。

**根因：** `undoSnapshot` 保存整个 `sources`、`registry` 和订阅 URL Map；撤销时直接用旧快照替换当前状态。

### 3.2 修复要求

- 将撤销记录改为本次删除的必要数据：目标来源、关联节点/来源别名、该来源的会话订阅 URL 等。不要通过覆盖整个工作区实现撤销。
- 撤销基于最新工作区做合并，只恢复本次删除的来源及关联。
- 同连接节点当前已存在时，合并来源关系；保留当前用户别名、其他来源的数据和最新编辑结果，不以旧快照覆盖。
- 仅恢复目标来源的 URL，不整体替换 `subscriptionUrlsRef`，避免丢失期间新增的订阅地址。
- 保持当前方案、活动方案、选择和规则；恢复原节点连接 ID 后，原有引用可重新有效，但不回退期间对方案的修改。
- 被取消的旧刷新请求不能在撤销后复活写入；被删来源原本处于 loading 时，恢复成可操作状态，不伪装旧请求仍在进行。
- 保持现有单步撤销语义即可，不要求实现通用撤销历史。再次删除另一来源时，撤销只针对最近一次删除；已执行的撤销不能重复追加节点。
- 成功导入或恢复另一工作区后，应清除旧工作区的撤销记录，不能将旧来源恢复到新工作区。

### 3.3 必需回归测试

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| R01-T01 | 删除 A → 新增 B → 撤销 A | A 恢复，B 及其节点、会话 URL 保留 |
| R01-T02 | 删除 A → 修改其他节点别名或方案选择 → 撤销 A | 期间的编辑结果保留 |
| R01-T03 | 删除 A → 刷新来源 C 并得到新结果 → 撤销 A | C 保持刷新后的节点及状态 |
| R01-T04 | A、C 共享节点 → 删除 A → 撤销 A | 节点不重复，来源关系恢复，C 的数据不回滚 |
| R01-T05 | 连续删除 A、B → 撤销最近一次删除；再次触发撤销 | 只恢复 B，不恢复 A，也不产生重复数据 |

## 5. R03：普通节点链接不得静默丢失 WebSocket 参数

### 5.1 复现输入

```yaml
proxies:
  - name: ws
    type: vless
    server: ws.example.invalid
    port: 443
    uuid: 00000000-0000-0000-0000-000000000000
    tls: true
    network: ws
    ws-opts:
      path: /socket
      headers:
        Host: ws.example.invalid
        Authorization: Bearer-REDACTED
      max-early-data: 2048
      early-data-header-name: Sec-WebSocket-Protocol
```

**实际结果：** 这些参数进入归一化节点；`validateNodeForFormat(node, 'import-links')` 返回空诊断，导出的 VLESS URI 只保留 path、Host 等字段，丢失 Authorization 和 early-data 设置。

这不是“普通链接不携带串联关系”的预期限制，而是单个节点连接参数被改变。依赖这些参数的节点无法等价还原。

### 5.2 修复要求

- 在统一目标格式校验中检查 WebSocket 参数是否可以被当前普通链接格式及目标客户端可靠表达。
- 默认保守处理：自定义请求头、early-data 或其他未实现的连接参数无法完整表达时，对 `import-links` 返回错误并阻止导出，指出具体字段。
- 若实现参数映射，必须有明确兼容依据及解析/导出往返测试；不得发明客户端无法识别的查询参数后就宣称支持。
- 标准 path + Host 的已有可表达场景保持可用；Host 头名称按大小写不敏感处理，或在归一化时规范化，不能漏掉 `HOST` 等写法。
- 保护覆盖“方案节点链接”“节点库单独导出”以及库中的高层生成接口，不能仅禁用某一个 UI 按钮。
- 诊断仅作用于无法表达该字段的目标格式。完整 Mihomo YAML 和配置片段能保留这些参数时仍应正常生成，不能一并禁用。
- 保持普通链接不包含链式编排的现有说明，不因此把参数丢失降级成无关提示。

## 6. R04：总超时覆盖 DNS 等待

### 6.1 复现与根因

向 `fetchSubscriptionWithRedirects` 注入永远不返回的 `lookup`，将总超时设为 20 毫秒。复审在约 150 毫秒后观察，请求仍处于 pending。

根因是超时只触发 `AbortController`；`await resolveAndValidateTarget(...)` 内部直接等待不支持该 signal 的 DNS Promise。只有 DNS 自己返回之后，后续流程才有机会发现超时。等待 DNS 期间的外部取消也存在相同缺口。

### 6.2 修复要求

- 将 DNS 等待纳入同一个总截止时间及取消机制，例如通过受 AbortSignal 控制的等待包装与 DNS Promise 竞争；不要求使用平台并不存在的 DNS 取消 API。
- 区分“停止等待并返回错误”与“取消底层系统 DNS 查询”，不能宣称已取消无法取消的底层操作。
- 保留整条链路的唯一总预算，包含每跳 DNS、建连、重定向和正文读取，不按阶段或每跳重置计时器。
- 截止时间触发后及时返回 `upstream_timeout`，HTTP 层按现有约定映射为 504。
- 外部取消按已有取消语义处理；不能一直等待 DNS 才结束。响应已断开时不继续尝试写成功响应。
- DNS 延迟成功或延迟失败时，不得继续建立上游连接、改写先前结果或产生未处理的 Promise rejection。
- 成功、超时、取消、DNS 错误等路径均清理监听器和计时器，检查发起连接前的取消状态。
- 继续保留 DNS 结果的 SSRF 校验、固定连接地址、Host/TLS SNI/证书校验；不能用跳过 DNS 检查或放松白名单换取超时通过。

### 6.3 必需回归测试

| 用例 | DNS 行为/操作 | 预期 |
| --- | --- | --- |
| R04-T01 | DNS 永不返回，触发总截止时间 | 及时以超时失败，不发起上游请求 |
| R04-T02 | DNS 等待期间用户取消/客户端断开 | 及时结束，不等 DNS 返回；不继续写响应 |
| R04-T03 | 超时/取消后 DNS 才成功或失败 | 不建连、不改写结果、无未处理 rejection |
| R04-T04 | 多跳中前一跳已消耗部分预算，下一跳 DNS 变慢 | 共用总预算，不重新获得完整超时时间 |
| R04-T05 | DNS 正常、DNS 返回禁止地址、正常 TLS/HTTP 拉取 | 正常路径可用，地址校验与 DNS 固定连接仍有效 |

使用可控 DNS Promise、请求 spy 和 fake timers 等方式稳定验证。不要依赖真实 DNS 故障，也不要用极窄的真实耗时断言制造 CI 偶发失败。至少一项测试证明超时后 HTTP 层的错误映射正确。

## 7. R05：刷新订阅保留用户别名

### 7.1 复现与根因

1. 导入只由一个订阅来源提供的节点，原名为 `entry`。
2. 将显示别名改为“自定义别名”。
3. 用完全相同的订阅内容刷新该来源。

**实际结果：** 别名重新变为 `entry`，即使连接 ID、凭据均未改变。

**根因：** `upsertSourceNodes` 先移除当前来源关联；独占节点因此从临时 registry 消失，后续被当成新节点重建，`displayName` 重新赋值为订阅原名。

### 7.2 修复要求

- 区分来源提供的名字与用户显示别名；建议记录显式用户覆盖值或覆盖标记，不仅使用一个会被刷新覆盖的字符串。
- 按稳定连接身份关联刷新前后节点。连接没有改变时，保留用户覆盖、选择及方案引用，同时更新来源原始别名和解析数据。
- 即使订阅服务修改了该连接的原名，用户设置过的显示别名仍优先。
- 没有用户覆盖时，可以按明确、可预测的规则展示来源原名；不要为保留别名而让所有节点名字永远无法更新。
- 多来源共享节点时，刷新或删除某一来源不重置用户别名。来源别名映射只更新对应来源，其他来源关系保留。
- 凭据或传输参数改变导致新连接 ID 时，不按同名自动继承旧节点身份或悄悄替换方案所选节点；继续提示旧引用失效。
- 若新增用户覆盖字段，同步主动保存/恢复与方案文件校验，兼容已有 `schemaVersion: 1` 数据。默认不含凭据的保存策略保持不变。
- 与 R01 共用一致的合并规则，避免“刷新保留了别名，但撤销删除再次覆盖”的交叉回归。

### 7.3 必需回归测试

| 用例 | 操作 | 预期 |
| --- | --- | --- |
| R05-T01 | 单来源节点改别名 → 相同内容刷新 | 用户别名、节点 ID 和方案选择保持 |
| R05-T02 | 改别名 → 来源原名变化但连接不变 | 用户别名保持，来源原名信息更新 |
| R05-T03 | 未改别名 → 来源原名变化 | 按声明规则更新显示，身份和选择不变 |
| R05-T04 | 多来源共享 → 刷新/删除一个来源 → 保存恢复或撤销 | 用户别名与其他来源信息保持 |
| R05-T05 | 同名同地址但凭据改变 | 创建新连接身份，旧引用明确失效，不静默移接 |
